Why lawgate

AI agents write most of the code. People still decide the rules.

People write the laws

A law is one sentence in LAWS.md that says what the code must never do. An agent can read it. Only the owner can change it.

Every law has a source

A law cites a file in the repository, a URL or a dated owner decision. It also names what enforces it: a machine, a test or a script.

A law has to bite

The gate switches the protected behaviour off and reruns the enforcer. If the test still passes, the law fails. A test that cannot fail proves nothing.

Rule changes need the owner

lawgate lists every file that declares or enforces a rule and checks that CODEOWNERS names the owner for each one. The platform then requires the owner's review.

It fails closed

A missing module, a crashed runner, an empty report or a test that did not run fails the gate. Nothing is shown green because it was skipped.

One command

lawgate check runs everything listed in lawgate.json and writes a Markdown summary, an HTML page and JUnit files.

How it works

Four layers, from the written law to the proof.

  1. 1Laws

    LAWS.md · package lawsdoc

    Each law has a source, an enforcer and a status. The gate checks that the enforcer exists, names the law and ran to completion.

  2. 2Machines

    packages machine, resolve

    A worker's control flow is declared as data. Laws are checked over that graph, and every declared site is bound to the Go source, so the two cannot drift apart.

  3. 3Typed states

    packages gen, run

    Generated state types only have the declared edges, so an undeclared move does not compile. At run time the trace refuses a move the machine does not allow.

  4. 4Kernels

    package prove

    A small pure function is checked on every input inside declared bounds. Within those bounds a pass is a proof, not a sample.

You can adopt layer 1 alone and add the others when a module needs them. The concepts guide explains each term with an example.

Quickstart

Adopt lawgate in five steps.

Install a pinned release with Go 1.25 or later

{{ $install }}

Or run it from a checkout of lawgate

go run ./cmd/lawgate check

  1. 1Run lawgate init

    It finds one module for each go.mod and writes lawgate.json, an empty readability baseline, a CODEOWNERS block and the CI file. It never overwrites an existing file.

    lawgate init --platform github --owner @your-org/law-owners

  2. 2Write LAWS.md

    One section for each law: what it forbids, where it comes from, what enforces it and its status. Name the law in the test that enforces it.

    ### rejects-empty-payload

Processing a job with an empty payload fails.

- Source: owner decision 2026-11-20
- Enforced by: test `TestRejectsEmptyPayload`
- Status: agreed 2026-11-20

  3. 3Run lawgate check

    Run it before every commit. It prints a fresh report directory under laws-report and exits 1 when a law is broken or a check could not run.

    lawgate check

  4. 4Require the CI jobs

    init wrote .github/workflows/lawgate.yml (or .gitlab-ci.yml). Require its two jobs, review-rules and check-laws, on the protected branch. They check the merge candidate, not the branch head.

    lawgate check-codeowners --base "$LAW_BASE"
lawgate rule-changes "$LAW_BASE" "$LAW_HEAD"
lawgate check

  5. 5Keep CODEOWNERS exact

    Require code-owner review on the protected branch. When rule files change, regenerate the entries and check that the owner covers every one.

    lawgate codeowners --fallback > .github/CODEOWNERS
lawgate check-codeowners

The user guide covers each step in full. When the gate fails, see troubleshooting. To work on lawgate itself, see the developer guide.
