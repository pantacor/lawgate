Why lawgate

AI agents write most of the code. People still decide the rules.

People write the laws

A law is one sentence in LAWS.md that says what the code must never do. An agent can read it. Only the owner can change it.

Every law has a source

A law cites a file in the repository, a URL or a dated owner decision. It also names what enforces it: a machine, a test or a script.

A law has to bite

The gate breaks the protected code on purpose, one condition at a time, and reruns the law's test. If the test still passes, the law fails. A test that cannot fail proves nothing.

Rule changes need the owner

lawgate lists every file that declares or enforces a rule and checks that CODEOWNERS names the owner for each one. The platform then requires the owner's review.

It fails closed

A missing module, a crashed runner, an empty report or a test that did not run fails the gate. Nothing is shown green because it was skipped.

One command

lawgate check runs everything listed in lawgate.json and writes a Markdown summary, an HTML page and JUnit files.

How it works

Four layers, from the written law to the proof.

  1. 1Laws

    LAWS.md · package lawsdoc

    Each law has a source, an enforcer and a status. The gate checks that the enforcer exists, names the law and ran to completion.

  2. 2Machines

    packages machine, resolve

    A flow, such as a checkout, is declared as data: its steps and their order. Laws are checked over that graph, and every declared site is bound to the Go source, so the two cannot drift apart.

  3. 3Typed states

    packages gen, run

    Generated state types only have the declared edges, so an undeclared move does not compile. At run time the trace refuses a move the machine does not allow.

  4. 4Kernels

    package prove

    A small pure function is checked on every input inside declared bounds. Within those bounds a pass is a proof, not a sample.

You can adopt layer 1 alone and add the others when a module needs them. The concepts guide explains each term with an example.

How it works, in plain words

  1. 1A person writes the rule

    One sentence, in a file called LAWS.md. It says what must never happen. That is the law.

  2. 2A test checks the rule

    An ordinary test, which the AI can write. The law names the test that guards it.

  3. 3lawgate checks the test

    It breaks the protected code on purpose, in every way it can find, and runs the test again. If the test still passes, the test proves nothing, and the change is refused.

  4. 4The owner guards the law

    The law, its test and the code it protects are pinned in LAWS.lock and cannot change without the owner's review. CI also reruns the approved test against every change. An AI cannot quietly rewrite them.

For developers: three ways to get past the law, with the real output of each

Same wallet, same law. We made each change and ran the commands. The gate output is trimmed to the lines that matter.

  1. Attempt 1 · refused

    Change the code

    The agent deletes the balance check. A wallet with $36 can now pay $900.

    The law's test fails. Any test suite catches this one. The next two are where ordinary CI stops helping.

    The gate refuses the change. It names the law's test and shows why it failed.

  2. Attempt 2 · refused

    Change the test too

    The agent keeps the broken code and rewrites the test. It now expects the $900 payment to succeed. It even regenerates LAWS.lock so the fingerprints match.

    go test is green. A normal pipeline would merge this.

    lawgate is not looking at the colour of the test. CI takes the test the owner approved, from the base commit, and runs it against the new code: it fails. The checkout also declares a balance check the code no longer has, and Pay has no condition left that a test could depend on.

    The gate refuses the change. A green test is not enough.

  3. Attempt 3 · refused, and needs the owner

    Delete the law

    The last shortcut is to remove the rule itself from LAWS.md.

    The gate still refuses. The base commit agreed that law, so removing it needs the owner to allow it in the approved lock first.

    And even a change that passed every check would wait here. The law document, the lock, the code and the test are rule files. CODEOWNERS names the owner for each one, so the platform will not merge the change without the owner's review.

    Refused, and waiting for the owner. The audit shows exactly which rule files the change touched.

Three kinds of law

A law, its code and its proof.

The wallet has three laws, one of each kind. Each has the same three parts: a sentence in LAWS.md, code that checks it, and proof that the check can fail.

Test law

One case, checked by a test. This is the law from the demo above: you can never spend more than you have.

Machine law

A law about the order of steps. The checkout is declared as a small machine: check the balance, then take the money.

Kernel law

A law about a small pure function, checked on every input inside declared bounds. Here: a refund can never take money away.

The wallet module is an illustration and is not in the repository; every output here comes from running lawgate on it. The repository has its own example module. The concepts guide explains witnesses, mutation, the lock and kernels.

Quickstart

Adopt lawgate in five steps.

Install a pinned release with Go 1.25 or later

{{ $install }}

Or run it from a checkout of lawgate

go run ./cmd/lawgate check

  1. 1Run lawgate init

    It finds one module for each go.mod and writes lawgate.json, an empty readability baseline, a CODEOWNERS block and the CI file. It never overwrites an existing file.

    lawgate init --platform github --owner @your-org/law-owners

  2. 2Write LAWS.md

    One section for each law: what it forbids, where it comes from, what enforces it and its status. Name the law in the test that enforces it.

    ## never-spend-more-than-you-have

No payment is accepted when it is larger than the balance.

- Source: owner decision 2026-11-23
- Enforced by: test `TestNeverSpendMoreThanYouHave`
- Status: agreed 2026-11-23

  3. 3Run lawgate check

    Run it before every commit. It prints a fresh report directory under laws-report and exits 1 when a law is broken or a check could not run.

    lawgate check

  4. 4Require the CI jobs

    init wrote .github/workflows/lawgate.yml (or .gitlab-ci.yml). Require its two jobs, review-rules and check-laws, on the protected branch. They check the merge candidate, not the branch head.

    lawgate check-codeowners --base "$LAW_BASE"
lawgate rule-changes "$LAW_BASE" "$LAW_HEAD"
lawgate check

  5. 5Keep CODEOWNERS exact

    Require code-owner review on the protected branch. When rule files change, regenerate the entries and check that the owner covers every one.

    lawgate codeowners --fallback > .github/CODEOWNERS
lawgate check-codeowners

The user guide covers each step in full. When the gate fails, see troubleshooting. To work on lawgate itself, see the developer guide.
